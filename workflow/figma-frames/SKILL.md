---
name: figma-frames
description: Implement a Figma design drawn as several state frames (filled, verifying, failed, success, confirm dialog) through TemPad Dev — pick the current frame of each state off a busy canvas, read its spec notes, build every state, compare a screenshot of each against its frame. Use when given a figma.com link or asked to apply, match or compare a UI against a Figma design.
---

The design is read through TemPad Dev's MCP (`get_structure`, `get_code`, `get_screenshot`), which reads the Figma tab open in Chrome; the Figma REST API is not used. Turning one frame into project code follows TemPad's `figma-design-to-code` skill. This skill adds what a multi-state design needs around it: which frames, which states, what the notes require, and proof that each state matches.

1. **Connect.** `list_design_sessions` shows the Figma files open with TemPad's MCP access on. None, or not the file of the link: ask the user to open that file in Chrome and turn on Preferences → Agent integration → MCP access. A link's `node-id=41240-234783` is the node id `41240:234783`. Done: the session for the right file.
2. **Find the frames.** `get_structure` on the link's node or the user's selection (`options.depth: 1` for a whole section). A canvas often holds several generations of one screen: the current ones sit beside the spec notes (`Note`, `規格說明`), and state frames are named by state (`f1 填寫`, `f3 驗證失效`). Read every note's text with `get_code`. Done: one frame id per state, and every note beside them read; the notes are requirements.
3. **Look at each state.** `get_screenshot` per frame, then name what differs between the states. Done: a list of states, each with what it shows that the others do not.
4. **Read the content.** Skip the app chrome every frame repeats (menu, nav bar, sidebar, footer, background) and `get_code` the content container (often `Card` or `Content`). A result whose code says `omitted direct children` is a shell: read those child ids in order. Keep `tokens` (Figma variables, with a value per theme mode) and the `data-hint-design-component` variants (`Button[Type=TextBtn][Status=Primary]`): they map to project tokens and components more surely than raw hex. Done: every element of the change has its values, and every literal colour without a variable is listed.
5. **Implement** per `figma-design-to-code`, mapping onto the project's own style or token doc first. Build every state from step 3, including the transient ones a note describes (loading, confirm dialog, hover). When the frames change copy, list old and new text and ask before editing translations. Done: every state is reachable in the running app.
6. **Compare.** Screenshot each state in the running app at the frame's width and Read it beside that frame's `get_screenshot`. List what differs (layout, spacing, colour, type, missing or extra elements), fix, and re-shoot until only deliberate differences remain, each with its reason (a container narrower than the frame, a shared component left alone). Done: one screenshot per state, and the remaining differences with reasons.
